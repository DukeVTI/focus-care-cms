 Focus Health &amp; Wellbeing This document provides a comprehensive set of instructions for developing the Health &amp; Wellbeing module within the Focuscms platform, accessible via the specified URL structure (e.g., https://focuscms.netlify.app/dashboard/health-wellbeing ). The goal is to create a dynamic, data-capture focused page that integrates seamlessly with existing individual records, particularly the Risk Assessment and Care Plan. 1. Data Model &amp; Database Structure The core of the Health &amp; Wellbeing page requires a structured data model to support reporting and compliance. 1.1 Core Health Condition Data Table ( HealthConditionEntry ) A single table should be created or updated to store individual health entries. This table must link back to the Young Person's ID and include the following fields for each of the three mandatory categories ( HealthCondition , SubstanceMisuse , MentalHealthCondition ): Field Name Data Type Description Constraints CategoryID Enum / String Defines the category: Physical , Substance , or MentalHealth . Required ConditionName String The specific condition selected from the dropdown, or "Other" if free-text is used. Required FreeTextCondition String Used only if ConditionName is "Other". Nullable Rating Integer A standardized rating to quantify the severity/impact of the condition. Required (e.g., 1-5 scale) Comment Text The free-hand text box for additional details related to this specific condition. Required/Optional based on business rules DateRecorded Date/Time Timestamp of the entry/last update. Required RecordedByUserID Integer ID of the staff member who logged the data. Required Export to Sheets 1.2 Medical Visits Table ( MedicalAppointmentLog ) A dedicated table to track appointments and visits. Field Name Data Type Description Constraints VisitType Enum / String GP , Hospital , Dental , Optician . Required DateOfVisit Date The date the appointment took place. Required ProviderName String Name of the GP, Hospital, Dentist, etc. Required OutcomeNotes Text Summary of the visit, diagnosis, or treatment plan. Required AppointmentDate Date/Time For recording future appointments (Dental/Optician). Nullable Export to Sheets 2. Front-End (UI) Implementation The page should be logically segmented into five distinct sections: 2.1 The Three Core Assessment Sections For Existing Health Conditions , Substance Misuse , and Mental Health Conditions , the UI must implement a dynamic, repeatable component structure: Condition Dropdown : A multi-select or additive dropdown menu. Dropdown Population : The list must contain the 20 most popular options (as derived from public health data in similar contexts) plus a final "Other" option. Health Conditions Examples (Top 20 List): Asthma, Allergies (Hay Fever/Food), Eczema/Dermatitis, Diabetes (Type 1/2), Epilepsy, Chronic Pain, Migraines, Irritable Bowel Syndrome (IBS), Severe Acne, Hearing/Vision Impairment, High Blood Pressure, Autoimmune Disorder, Sleep Disorder, Physical Disability, Long-term Injury, Contagious Illness (specify), Iron Deficiency, Chronic Fatigue, Gynaecological Condition (specify), Other. Substance Misuse Examples (Top 20 List): Cannabis, Alcohol, Nicotine/Vaping (High Use), Powder Cocaine, Ecstasy (MDMA), Ketamine, Solvents/Inhalants (Glue/Gas/Aerosols), Benzodiazepines (e.g., Xanax), New/Synthetic Psychoactive Substances (NPS), Amphetamines, Heroin, Crack Cocaine, Fentanyl/Other Opiates, Codeine/Prescription Misuse, Volatile Substance Use, Steroids, Hallucinogens, Laughing Gas (Nitrous Oxide), Multiple Substances (Polydrug Use), Other. Mental Health Conditions Examples (Top 20 List): Depression, Generalised Anxiety Disorder (GAD), Social Anxiety, Eating Disorder (Specify: Anorexia/Bulimia/BED), Self-Harm/Suicidal Ideation, Post-Traumatic Stress Disorder (PTSD), Obsessive-Compulsive Disorder (OCD), Attention Deficit Hyperactivity Disorder (ADHD), Autism Spectrum Disorder (ASD), Psychosis/Schizophrenia, Bipolar Disorder, Borderline Personality Disorder (BPD), Conduct Disorder, Phobias (Specific/Social), Unspecified Emotional Disorder, Attachment Disorder, Adjustment Disorder, Dissociative Disorder, Tics/Tourette's Syndrome, Other. Associated Rating Option : For each selected condition, a rating input is required. Implementation: Use a radio button or slider input with a clear, defined scale (e.g., Severity Scale 1-5 where 1=Low Impact/Well Controlled, 5=Severe Impact/Crisis). Additional Comments Field : A free-hand text area must be provided per condition (not per section) to allow the Keyworker to detail the condition's history, current impact, and treatment. 2.2 Linkage Section Clearly display read-only links to the individual's: Risk Assessment Care Plan 2.3 Medical Visits Log Section A dedicated area to log the required medical visits, utilizing the MedicalAppointmentLog data structure. Input fields for: VisitType (Dropdown), DateOfVisit , ProviderName , OutcomeNotes . A separate subsection for Dental and Optician information, including an input for AppointmentDate to track future check-ups. 3. Backend Logic &amp; Integrations 3.1 Risk Assessment &amp; Care Plan Synchronization Incident Trigger: The platform must implement a logic hook such that any new incident recorded (in the general incident module) or any health-related incident recorded (e.g., a mental health crisis logged on the Health &amp; Wellbeing page, or a Rating of 5 being submitted) MUST trigger a mandatory prompt for the staff member to review and update the individual's Risk Assessment. Implementation: A persistent, non-dismissible notification or pop-up should appear upon saving the triggering event, with a link to the Risk Assessment page and a mandatory tick-box confirmation that the Risk Assessment has been updated/reviewed. Risk Rating Notification Logic: The system must monitor the Risk Assessment status. When either of the following events occurs, an automated email notification must be sent: a) The Risk Assessment is updated (i.e., new version saved). b) The Risk Assessment is explicitly flagged/rated as "High Risk" (or the platform's equivalent highest rating). Notification Recipient List: The email notification must be sent automatically to pre-defined user roles associated with the young person: Keyworker Manager PA (Personal Assistant/Relevant Admin) 3.2 Data Visualization The system must be designed to collate the Rating data across the platform to support analysis. Reporting API: Create an endpoint capable of aggregating the HealthConditionEntry.Rating data based on: Individual: Trend over time for a single Young Person. Group/Cohort: Aggregated analysis (e.g., average rating, distribution of ratings) filtered by condition ( ConditionName ), user demographics, or staff groups. Front-end Integration: Ensure the platform has or is designed to integrate with visualization libraries (e.g., Chart.js, D3.js) to render this aggregated data as: Graphs (e.g., line charts for trends, bar charts for comparisons). Pie Charts (e.g., distribution of severity ratings across a cohort). 4. Task and Calendar Integration The platform must allow staff members to immediately create a follow-up action (a Task/Reminder) and/or schedule a Calendar Event when saving a Health Update. 4.1 UI/Workflow Implementation Action Creation Checkbox: When a staff member is saving a new or modified entry in the three core assessment sections ( Physical , Substance , or MentalHealth ), a new optional section labeled "Schedule Follow-up Action" must be presented. This section should be activated by a checkbox (e.g., "Create a follow-up task/event"). Input Fields (Conditional Display): Upon activation, two distinct creation modes should be available, or a unified input if the underlying system supports seamless synchronization: Action/Task Input: Title/Action Description (Required): A field for the staff member to define the specific action (e.g., "Call GP to follow up on medication"). Due Date/Time (Optional): Input for the required completion time. Calendar Event Input: Event Date/Time (Required): Input for the specific date and time the follow-up event should occur. Duration (Optional): Time length of the calendar entry. Attendees (Optional): Option to add other relevant staff members (Keyworker, Manager, etc.) to the calendar event. Default Linking: The Young Person's Name and a reference to the specific Condition Entry ID must be automatically appended to the Title or Description of the created Task/Calendar Event to maintain context. 4.2 Backend API Logic Upon saving the Health Update entry (Section 1.1) and if the "Schedule Follow-up Action" is checked, the Focuscms backend must execute calls to the integrated Reminder and Calendar systems. API Call Logic (Task/Reminder): If a Task/Action is requested: The backend must call the internal API wrapper for task creation (conceptually equivalent to Tasks/ Reminders:create ). title : Use the user-provided title + auto-appended young person/condition reference. start_datetime : Use the user-provided Due Date/Time, formatted as yyyymmddTHHMM . API Call Logic (Calendar Event): If a Calendar Event is requested: The backend must call the internal API wrapper for calendar event creation (conceptually equivalent to Calendar:create ). title : Use the user-provided title (or a default like "Health Follow-up Action for [Young Person Name]"). start_datetime : Use the user-provided Event Date/Time, formatted as yyyymmddTHHMM . calendar_id : The calendar event MUST be created on the individual Young Person's dedicated calendar (if one exists) or the Keyworker's primary calendar if a dedicated one is not available, to ensure it is visible and trackable. Data Linkage &amp; Audit: The IDs returned from both the Task creation and Calendar Event creation APIs must be stored in the HealthConditionEntry or a dedicated audit log table. This ensures direct traceability from the Health Update entry to the created follow-up action. Mandatory Integration: The system must ensure that the created Task/Event is integrated into the individual’s calendar/task list as per the request, allowing the Keyworker and relevant staff to track the action alongside all other scheduled activities. This requires the backend service account to have appropriate permissions to create events in the specified calendars. The data collected must be chartable e.g. the amount of young people that are cannabis user etc
